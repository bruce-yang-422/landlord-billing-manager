# 架構方向與重寫評估

記錄日期：2026-11-17

## 目前決定

暫不為了更換技術棧而全面重寫。現有原生 JavaScript 架構仍可滿足目前需求，優先依實際需求局部改善。

目前只有開發者本人使用，尚無其他使用者。這降低了未來遷移的成本，但本身不構成重寫的理由。本文件記錄方向，不代表已決定開始實作。

## 評估過的技術組合

Vue 3 + Vite + TypeScript + Naive UI 技術上可行，主要收益為可維護性：

| 技術 | 預期收益 | 成本與限制 |
| --- | --- | --- |
| Vue 3 | 以狀態驅動畫面、共用帳單與表單元件，減少手動同步 DOM | 需重寫畫面與事件，仍須拆分業務邏輯才有實質收益 |
| TypeScript | 明確定義帳單、抄表、儲值與抵扣資料，協助發現欄位漏改 | 不保證公式正確；外部資料仍需執行期驗證 |
| Vite | 模組化開發與正式建置流程 | 增加建置與套件維護，部署及 PWA 快取須調整 |
| Naive UI | 統一表單、表格、確認視窗與主題 | 增加依賴，手機操作與版面仍須自行設計及驗收 |

更換技術棧不會自動提升計算正確性、效能或下載體積，也不會直接提供多房源或跨裝置同步。

## 現有架構可先改善之處

`js/ui.js` 同時處理 DOM 讀值、驗證、計算預覽、存檔、報表及歷史畫面。後續有相關修改需求時，可逐步將計算、儲值與資料存取邏輯抽離，讓畫面只負責輸入與呈現。

保留既有計算案例與測試作為行為基準。評估當時執行 `node --test tests/*.test.cjs`，84 項測試全部通過；此結果不代表已完成瀏覽器操作與離線驗證。

## 何時重新考慮全面重寫

- 持續新增功能、頻繁調整操作流程，現有 DOM 與狀態同步開始造成明顯維護負擔。
- 準備支援更多房間、不同電號或多房源，需要重新設計資料模型。
- 有具體介面需求，且元件化帶來的收益足以抵銷重寫與回歸驗證成本。

若只是維持既有功能、修正細節或改善外觀，優先局部修改，不必全面換框架。

## 若未來決定重寫

可直接以新架構重寫，不要求漸進替換、雙版本並行，或讓新版直接相容舊資料格式。

資料遷移方式：

1. 先從目前版本匯出完整備份，保留原始檔。
2. 提供獨立、一次性的轉換工具，只需支援本人當時實際匯出的格式，不必涵蓋所有歷代備份。
3. 工具驗證來源並產出新版備份，核對各戶帳單筆數、各項費用、應收金額、抄表、儲值與抵扣餘額；列出無法轉換的項目，不靜默丟棄資料。
4. 新版只處理自己的資料格式，採獨立 localStorage key，資料與備份帶有版本號。

歷史帳單保留原始金額、抵扣與備註，不以新版算法重算。未存檔輸入、主題及顯示偏好可重設。

新版完整備份可考慮帶版本號的 JSON，CSV 作為試算表匯出用途；此為建議，實作前再確認。

重寫時仍須保留現有帳務規則與功能，包括跨季電費、抄表邊界、尾差、水費入住天數、逐項抵扣、刪除返還、歷史快照及報表資訊隔離。既有測試案例應移植為新架構的驗收基準。

即使不保留資料格式相容層，同網址部署仍須處理舊 Service Worker 接管與快取清理。Vite 建置資源、GitHub Pages 子路徑、離線使用與更新流程需另外驗證。
